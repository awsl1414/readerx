# ReaderX Web 设计指南

> 阅读产品最后会安静到几乎感觉不到设计存在。

## 0. 元原则

本文档不是设计教义。它是一组约束，用来防止我们做出"看起来高级但用起来累"的东西。

当本文档的任何规则与用户阅读体验冲突时，**扔掉规则**。

### 不做什么

明确边界比做加法更重要。ReaderX：

- **不做社交**。没有关注、动态、评论、分享到社交网络。
- **不做社区**。没有书评广场、排行榜、读者圈。
- **不做推荐算法**。书架是用户自己的，不是算法投喂的。
- **不做 gamification**。没有阅读时长、连续打卡、成就徽章。
- **不做在线同步**。当前阶段数据全部本地（IndexedDB + OPFS）。
- **不做多人协作**。单人工具。
- **不做 AI 总结/问答**。AI 增强是独立可选包，核心阅读流不依赖它。

ReaderX 是一个**私人阅读工具**。管理是手段，阅读是目的。

## 1. 核心价值排序

设计决策冲突时，按此顺序取舍：

```
1. 快         — 瞬时感，操作零延迟
2. 稳         — 认知稳定，可预测，不意外
3. 安静       — UI 退让，内容始终是主角
4. 简单       — 路径短，层级少，概念少
5. 好看       — 精密但不抢戏
```

**快排在第一位。** 不是"快且好看"，是"快，然后在快的基础上好看"。

### 速度哲学

阅读产品最重要的感知是**瞬时感（instantaneous）**——操作和反馈之间零间隔。

| 场景 | 目标 |
|---|---|
| 点击书籍进入阅读 | < 200ms 可见反馈 |
| 翻页 | 下一帧即显示，无动画延迟 |
| 切换章节 | < 300ms 内容替换 |
| 搜索出结果 | 流式返回，不等全部 |
| 打开设置 | 即时，无加载态 |

**动画永远不能阻塞操作。** 任何 transition 都可以用操作打断。高频使用后动画应自动减弱（见 §7 渐进退化）。

### 认知稳定性

用户第 300 次打开书时，不应该还在"感受设计"。

- 同一个操作，永远在同一个位置触发，永远产生同一个结果。
- UI 元素的位置固定，不随上下文变化而移动。
- 返回行为可预测：Esc / 返回手势永远回到上一状态，没有例外。
- 颜色、字号、间距不因页面而异——全局一致。

**稳定 > 聪明。** 如果一个"智能"行为可能让用户困惑，用"笨但稳定"的方案。

## 2. 导航：简单的路由，不是空间实验

### 架构

ReaderX 有 4 个一级区域：

```
首页    — 状态恢复中心：继续阅读 + 最近在读
书库    — 全部书籍，分组管理
搜索    — 多书源搜索
设置    — 书源管理 + 阅读设置 + 系统设置
```

移动端是 4 Tab 底栏。桌面端是侧边栏。

### Discover 为什么不是一级入口

ReaderX 的核心是"私人阅读工具"。用户来这里是为了读自己已经有的书，或者搜索特定的书。没有推荐算法、没有社区、没有热门榜。

"发现"功能如果有，应该是搜索的增强（如热门搜索词），而不是独立的信息架构分支。

### 导航行为

- 路由用 Next.js App Router，正常的 URL 路由，不搞 parallel routes 黑魔法。
- 页面切换用简单的 cross-fade（150ms），不用 morph / shared element transition。
- 浏览器前进后退正常工作。URL 是用户可理解、可分享的。
- 阅读器是唯一全屏状态，进入/退出用简单的 fade + scale，不是 morph。

**为什么不用空间导航？**

空间连续导航（View Transitions + parallel routes + morph）在理论上优雅，但：
- 调试复杂度指数增长
- 移动端性能不可控（Safari / Android WebView）
- hydration 问题频发
- 用户不需要——用户需要的是"点击→看到内容"，不是"感受空间变化"

### 侧边栏（桌面端）

56px 宽，图标 + hover 文字，无背景无边框。

```
R (logo)     — 回首页
首页
书库
搜索
─────────────
设置         — 书源管理 + 阅读设置 + 系统
```

### 底栏（移动端）

4 Tab：首页 / 书库 / 搜索 / 设置。毛玻璃效果。

### 顶栏

毛玻璃（`backdrop-filter: blur(20px)` + 半透明背景）。页面标题 + 搜索入口 + 主题切换。

## 3. 信息密度：不均匀但稳定

### 视觉权重

首页是最佳示例：

```
权重 5（最强）—— 继续阅读 Hero
  封面 + 标题 + 进度条 + 一键进入
  这是首页存在的核心意义

权重 3 —— 最近在读
  小封面卡，横向滚动
  功能：快速切换

权重 2 —— 收藏分组
  Chips，单行，可交互

权重 1（最弱）—— 书库预览
  更小的封面，更低对比度
  功能：引导去书库完整页
```

### 规则

- 面积 = 重要性。
- 滚动 = 降低优先级。
- 高权重区域可交互，低权重区域只读。
- **间距严格一致**：卡片 12px，Section 28px，内容 padding 24px（桌面）/ 16px（移动）。

### 禁止

- 所有卡片等大的网格
- 所有文字等大的列表
- 无主次之分的 dashboard
- 每个区域相同 padding

## 4. 阅读行为模型

### 用户是谁

ReaderX 用户的核心行为：

| 模式 | 特征 | 设计响应 |
|---|---|---|
| 睡前读 | 躺着，单手，低光 | 暗色主题舒适、大点击区域、少蓝光 |
| 通勤读 | 碎片时间，网络不稳 | 离线优先、快速恢复位置、3 秒内进入阅读 |
| 连续阅读 | 长时间沉浸，1-2 小时 | UI 最小化、零打断、自动预取 |
| 跳章浏览 | 快速扫描目录、找特定章节 | 目录随时可达、搜索章节标题 |
| 回忆重读 | 找特定段落、角色、情节 | 全文搜索、书签、阅读历史 |
| 获取新书 | 明确知道要什么，搜索即走 | 搜索快、结果准确、一键加入书架 |

### 阅读节奏系统

系统根据用户行为模式调整 UI 行为：

```
连续阅读 > 20 分钟：
  → 控制层自动隐藏间隔延长（3s → 5s）
  → 动画减弱
  → 降低视觉打扰

快速跳转模式（1 分钟内切换 > 3 章）：
  → 导航元素更持久显示
  → 目录入口更显眼
  → 搜索入口增强

长时间未读（> 7 天）：
  → 不催促，不通知
  → 首页按最近阅读自然排序
```

**注意：** 这是微调，不是模式切换。用户不应该感知到"系统在适应我"。

## 5. 交互：直接优先

### 操作层级

| 层级 | 触发 | 示例 |
|---|---|---|
| **零操作** | 系统主动 | 继续阅读 Hero |
| **单操作** | 一次点击 | 点击封面进入阅读、切换 Tab |
| **上下文操作** | 在内容上操作 | 选中文字 → 浮出菜单 |
| **深层操作** | 侧边栏/设置 | 书源管理（Scraping Workspace）、导入 |

80% 的操作应该在「单操作」完成。超过 2 次点击到达的功能，考虑移位置。

### 上下文 UI

UI 在需要时出现，不需要时消失。但**出现的位置和方式必须稳定可预测**。

| 触发 | UI | 消失 |
|---|---|---|
| 阅读中点击 | 顶栏 + 底栏 | 3 秒无操作淡出 |
| 选中文字 | 操作菜单 | 点击空白 |
| 搜索输入 | 实时结果 | — |

**关键约束：** 上下文 UI 不移动已有元素。浮层用 overlay，不用 reflow。

### 返回行为

所有返回遵循同一规则：**Esc / 返回手势 = 关闭当前浮层或回到上一页**。

不允许出现：
- "按 Esc 后不知道回到了哪里"
- "返回后之前的滚动位置丢了"
- "返回后需要重新加载"

## 6. 故障设计

真正成熟产品最重要的不是正常流程，而是 broken state。

ReaderX 最大的风险是书源。真实世界：

- 规则失效（网站改版）
- 反爬（频率限制、验证码）
- 章节错乱（目录和正文不匹配）
- 编码异常（乱码）
- 图片失效（防盗链）
- 慢源（超时）
- 部分失败（目录成功但某章节失败）
- 完全失败（书源下线）

### 降级路径

| 故障 | 用户看到什么 | 系统做什么 |
|---|---|---|
| 单章获取失败 | 该章位置显示「加载失败」+ 重试按钮 + 跳过按钮 | 自动 retry 1 次，失败后记录，不影响其他章节 |
| 书源超时 | 搜索结果中该书源标记为慢，其他结果正常显示 | 超时 10s 后标记，后台继续等待 |
| 书源完全失败 | 搜索结果底部「N 个书源无响应」 | 不弹 toast，不阻塞 |
| 编码乱码 | 显示原文 + 「内容异常」提示 | 尝试备选编码自动修复 |
| 目录加载成功但正文失败 | 目录正常显示，失败章节灰色 + 重试 | 静默 retry，不丢失阅读位置 |
| 网络断开 | 阅读器继续显示已缓存内容，顶栏低调提示 | 缓存优先 |
| 所有书源失败 | 温和说明 + 修复指引 | 每个书源显示具体错误 |

### 故障原则

- **永远不弹 modal 阻塞阅读。** 错误信息用 inline 提示。
- **部分失败不影响整体。** 10 个书源 3 个失败，显示 7 个的结果。
- **保留用户状态。** 失败后重试不丢失阅读位置、搜索词、滚动位置。
- **给出操作路径。** 每个错误都有明确的"下一步"。
- **不恐慌。** 错误提示语气平和，不使用感叹号、红色警告色。

## 7. 动效：克制、快速、可退化

### 核心原则

动效不是装饰，也不是空间连续性的载体。动效的唯一目的是**帮助用户理解发生了什么**。

- **进入快**（100-150ms）
- **退出稍慢**（150-250ms）
- **阅读区无动效**——翻页就是翻页
- **所有动效可打断**
- **高频使用后自动减弱**

### 渐进退化

```
首次使用（前 10 次）：
  完整 transition（fade / scale）
  控制层 3s 后淡出

高频使用（同一操作 > 50 次）：
  transition 缩短至 50ms（几乎瞬间）
  控制层 2s 后淡出

超高频（同一操作 > 200 次）：
  instant（0ms），仅维持最基本的状态提示
```

实现：localStorage 记录高频操作计数，达到阈值后自动退化。用户可在设置中重置。

### 允许的动效

| 动效 | 时长 | 用途 |
|---|---|---|
| opacity fade | 100-150ms | 页面切换、浮层出现 |
| scale(0.98→1) + fade | 150ms | 弹窗 / Sheet 出现 |
| opacity fade out | 200ms | 控制层消失 |
| stagger fade-in | 每个 30ms | 搜索结果到达 |

### 禁止的动效

- bounce / spring 超过 200ms
- 旋转 loading（用 skeleton 替代）
- 全局 loading 转圈（用渐进加载替代）
- morph / shared element transition
- 任何超过 300ms 的过渡
- View Transitions API（复杂度不值得）
- `@starting-style` 大面积使用

## 8. 视觉系统

### Surface 层级（零 border）

通过背景明度区分层级，不用实线边框。

```
Surface 0  基底     侧边栏、最底层
Surface 1  内容     主内容区
Surface 2  提升     卡片、hover
Surface 3  悬浮     弹出层、active
Surface 4  模态     对话框 + backdrop-blur
```

暗色 token（oklch）：

```
Surface 0: oklch(0.13 0.01 260)
Surface 1: oklch(0.16 0.012 260)
Surface 2: oklch(0.19 0.014 260)
Surface 3: oklch(0.22 0.015 260)
```

亮色 token：

```
Surface 0: oklch(0.98 0.002 260)
Surface 1: oklch(0.995 0.001 260)
Surface 2: oklch(0.96 0.003 260)
Surface 3: oklch(0.93 0.004 260)
```

### 圆角

```
4px   badge、tag
8px   按钮、输入框
12px  卡片、chip
16px  Sheet、Modal
24px  页面容器
```

### 图标

减少图标依赖。导航用 Lucide 小图标，状态用颜色 + 小点，操作用文字标签。

### 阅读器排版

- 段落行距 ≥ 1.8em
- 左右留白 ≥ 40px（桌面）/ 20px（移动）
- 字号用户可调（14-24px）
- 零装饰性元素

## 9. 主题系统

两层独立：全局 UI 主题和阅读器主题互不影响。

**全局 UI 主题**：`light` / `dark` / `system`，用 next-themes + cookie + `.dark` class。

**阅读器主题**：

| 值 | 背景 | 文字 | 色调 |
|---|---|---|---|
| `warm-white` | oklch(0.98 0.005 80) | oklch(0.30 0.01 60) | 暖白 |
| `beige` | oklch(0.93 0.02 80) | oklch(0.28 0.02 60) | 米黄 |
| `green` | oklch(0.92 0.03 155) | oklch(0.25 0.02 140) | 护眼绿 |
| `sepia` | oklch(0.25 0.03 60) | oklch(0.75 0.03 70) | 深褐 |
| `black` | oklch(0.12 0 0) | oklch(0.65 0 0) | 纯黑 |

存储：Zustand + IndexedDB。只影响阅读器内容区 3 个 CSS token（`--reader-bg`、`--reader-text`、`--reader-text-secondary`）。

## 10. 多语言（i18n）

- 范围：UI 文字支持中文/英文。书源规则和小说内容不翻译。
- 方案：next-intl，无 URL 前缀。
- 检测：cookie → Accept-Language → 默认 zh。
- 切换：Server Action 写 cookie + router.refresh()。
- 所有用户可见文字通过 `t()`，零硬编码。

文件结构：

```
apps/web/
  messages/
    zh.json
    en.json
  i18n/
    request.ts
    routing.ts
```

## 11. 书源体验

书源是 ReaderX 的生命线。

### 生命周期

```
首次启动 → 无书源 → Onboarding 引导 → 导入（URL / JSON）
→ 逐个校验 + 进度反馈 → 首页显示就绪状态
→ 日常使用 → 异常时静默提示 → 用户主动管理
```

### 书源在 UI 中的位置

| 位置 | 桌面 | 移动 |
|---|---|---|
| 侧边栏/Tab | 设置内一级入口 | 设置内快捷入口 |
| 首页 | 状态卡片（N 个书源已就绪） | 同桌面 |
| 设置 | 书源管理（Scraping Workspace） | 同桌面 |

### 书源管理页 — Scraping Workspace

> 书源管理不是设置表单，而是 Scraping Workspace。详细设计见 `docs/superpowers/specs/2026-05-29-source-manager-design.md`。

桌面端三段式布局（列表 | 编辑器 | 调试器），移动端 stack navigation。

- **Layer 0 列表**：名称、域名、能力标记（`[JS]` `[Cookie]` `[CF]`）、启用开关。顶部筛选：全部 / 已启用 / 已禁用 / 异常。搜索书源名称。
- **Layer 1 编辑器**：可折叠规则分组（IDE 风格），Schema-aware Code Textarea（解析器类型提示 `[CSS]` `[XPath]` `[JSONPath]` `[JS]`）。
- **Layer 2 调试器**（一等公民）：Pipeline Timeline（阶段可视化）、Network Inspector（请求/响应详情）、Console（日志）。
- **导入**：Dialog overlay，支持 URL / 文件 / 粘贴，含兼容性分析报告。
- **能力检测**：静态扫描规则字段，推断 JS/Cookie/WebView/Cloudflare 需求。

## 12. 空状态

每个空状态是引导机会，不是"无数据"终点。

| 空状态 | 展示 | 行动 |
|---|---|---|
| 无书源 | Logo + 说明 + 3 种导入 | 引导首次书源配置 |
| 无书籍 | 书源就绪 + 搜索入口 | 引导搜索 |
| 搜索无结果 | 搜索词 + 建议 | 降低挫败感 |
| 阅读完成 | 章节完成 + 「下一章」 | 维持阅读流 |
| 书源全部失败 | 温和说明 + 修复指引 | 不恐慌 |
| 离线无缓存 | 插画 + 网络恢复提示 | 安静等待 |

原则：
- 永远不显示空白页。
- 每个空状态有且仅有一个主要行动按钮。
- 语气友好但不幼稚。
- 不使用动画（零 ambient motion）。

|---|---|---|---|

## 14. 命令面板（⌘K）

桌面端效率入口。用 cmdk（shadcn/ui Command）。

- 搜索书籍
- 导航页面
- 管理书源
- 快捷操作

弹出用简单的 scale + fade（150ms），不用复杂动效。

## 15. 技术实现映射

| 设计决策 | 技术实现 | 理由 |
|---|---|---|
| RSC 边界 | Server = shell/metadata only；Client = `<ClientApp>` 包裹整个运行时 | 重客户端应用（IndexedDB/Worker/QuickJS），RSC 无法参与 |
| 页面导航 | Next.js App Router，标准 URL 路由 | 简单、可调试、浏览器后退正常 |
| 毛玻璃顶栏 | `backdrop-filter: blur()` + oklch alpha | 视觉分层 |
| Surface 层级 | CSS custom properties | 全局 token |
| 动效 | CSS transition + opacity | 简单、高性能、无 hydration 风险 |
| 主题切换 | next-themes（cookie + `.dark`） | SSR 兼容 |
| 阅读器主题 | ReaderSession → CSS class | Session 管理，独立于全局主题和 Zustand |
| 阅读器状态 | ReaderSession 对象（非全局 store） | 分页/游标/缓存由 session 生命周期管理 |
| 阅读器渲染 | RenderModel → React 组件 + Render Scheduler | 布局失效由调度器驱动，不在 useEffect 中触发 |
| Worker 通信 | async bridge API（feature 不直接接触 Worker） | 解耦 UI 和 Worker RPC |
| 多语言 | next-intl（cookie 检测） | 无 URL 前缀 |
| 命令面板 | cmdk | 成熟方案 |
| 组件库 | shadcn/ui + Radix UI + Tailwind CSS v4 | 无样式锁定 |
| 字体 | Inter（UI）+ 系统衬线（阅读器） | — |
| 色彩 | oklch 全局，零 hex/rgb | 感知均匀 |

**刻意不用的技术：**
- ~~View Transitions API~~ — 复杂度不值得
- ~~Parallel Routes~~ — 非标准导航行为
- ~~`@starting-style`~~ — 浏览器支持不完整
- ~~Shared element transition~~ — morph 效果对阅读产品不必要
- ~~全局 reader Zustand store~~ — session 模式更合适，避免巨型 store

## 16. 阅读器

阅读器是 ReaderX 的核心，但设计上应该**最无聊**。

### 原则

- 全屏沉浸。侧边栏、顶栏全部隐藏。
- 控制层（顶栏 + 底栏 + 目录）：点击/轻触浮出，3 秒无操作淡出。
- 翻页无动画——就是内容切换。翻页方向可配置（左右 / 上下 / 滚动）。
- 字号、行距、主题用户可调。
- 进度自动保存，退出后恢复到精确位置。
- 上下章切换：控制层底部按钮。

### 架构

阅读器不使用全局 Zustand store，而是 ReaderSession 模式：

```text
ReaderSession
├── pagination state（分页结果缓存）
├── cursor（当前位置）
├── chapter cache（已加载章节）
├── prefetch queue（预取队列）
└── settings snapshot（字号/行距/主题快照）
```

- session 由 React 组件持有，组件卸载时 dispose
- 字号/行距变更 → session 内部触发重排 → 输出新的分页结果
- React 只负责渲染当前 viewport 可见的 pages
- 禁止 useEffect 触发重排：布局计算由 session 内部的 Render Scheduler 驱动

### 进入和退出

- 进入：简单的 fade in（150ms）。
- 退出：Esc / 返回手势 / 顶栏返回按钮，fade out（150ms）。
- 不搞 morph，不搞 shared element。

### 选中文字

选中文字后浮出菜单：复制 / 高亮 / 搜索。菜单位置紧贴选中区域，不遮挡内容。

## 17. 验收标准

- [ ] 第一次打开 App，30 秒内能开始阅读？
- [ ] 第二次打开 App，1 次点击能恢复阅读？
- [ ] 搜索到结果到进入阅读器，< 2 次点击？
- [ ] 阅读器中 UI 消失后，用户知道怎么唤出？
- [ ] 书源异常时阅读流被打断了吗？
- [ ] 单章失败时，其他章节正常？
- [ ] 中英文切换后所有文字正确？
- [ ] 暗色模式所有层级清晰？
- [ ] 移动端单手完成 80% 操作？
- [ ] 从点击到看到内容，体感是"瞬间"还是"在等"？
- [ ] 高频使用 300 次后，动画还是那么"精心设计"吗？（应该几乎消失了）
- [ ] 断网时能继续阅读已缓存内容？
